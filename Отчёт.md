# 1. Доменная область приложения

Веб-приложение для ведения дневника самоконтроля пациентов с сахарным диабетом (например, меня).

Функциональные возможности:
1. Учёт измерений уровня сахара в крови (ммоль/л).
2. Учёт инъекций инсулина двух типов: короткого и длинного действия (в условных единицах).
3. Учёт приёмов пищи с автоматическим расчётом углеводов и хлебных единиц(это 12 грамм углеводов).
4. Справочник продуктов с crud операциями и хранением содержания углеводов на 100 г.
5. Отображение событий и статистики за сегодня и вчера.

# 2. Стек реализации

Бэкенд:
- Python 3.11+
- FastAPI (веб-фреймворк)
- SQLAlchemy (ORM)
- Alembic (миграции БД)
- PostgreSQL 16 (СУБД)
- Pydantic (валидация данных)

Фронтенд:
- HTML5, CSS3, JavaScript 

Требования к окружению:
- Python 3.11+
- Docker Desktop (для запуска PostgreSQL)
- Git

# 3. Основные сущности доменной области

# 3.1. Food 
Справочник продуктов питания. 
Содержит название продукта и количество углеводов на 100 грамм.

# 3.2. GlucoseEvent
Запись об измерении уровня глюкозы в крови. 
Хранит время измерения, значение в ммоль/л.

# 3.3. InsulinEvent 
Запись о введении инсулина. 
Хранит время инъекции, тип инсулина (короткий или длинный), дозу в условных единицах.

# 3.4. MealEvent 
Запись о приёме пищи. Ссылается на продукт из справочника, хранит массу в граммах.

# 4. Соответствие методологии 12 факторов

# Фактор 1: Кодовая база
Весь код приложения (и бэкенд и фронтенд) находится в едином Git репозитории diabetes-diary
Развёртывание происходит из одного источника

# Фактор 2: Зависимости
Все зависимости явно объявлены в requirements.txt с фиксированными версиями
Установка производится командой pip install -r requirements.txt
Виртуальное окружение .venv изолирует зависимости от системы

# Фактор 3: Конфигурация
Конфигурация хранится в переменных окружения (файл .env)
Нету хардкода паролей или адресов БД
Используется pydantic-settings для загрузки настроек
Файл .env исключён из Git через .gitignore

# Фактор 4: Внешние сервисы
PostgreSQL рассматривается как подключаемый ресурс
Доступ осуществляется через URL из переменной DATABASE_URL
Замена локальной базы требует только изменения конфигурации, в код трогать не надо

# Фактор 5: Сборка, релиз, запуск

Этапы разделены:
1. Build: установка зависимостей (pip install) + сборка Docker образа
2. Release: применение миграций (alembic upgrade head)
3. Run: запуск сервера (uvicorn app.main:app или docker run)
Приложение контейнеризировано с помощью Docker.

# Фактор 6: Процессы
Приложение stateless
Все данные хранятся в PostgreSQL
В памяти процесса не сохраняется состояние сессий или пользовательские данные
Это позволяет безопасно перезапускать процессы

# Фактор 7: Привязка к порту
Приложение самодостаточно и экспортирует HTTP-сервис через порт 8000 с помощью Uvicorn
Не требуется внешний веб-сервер типа nginx/Apache

# Фактор 8: Параллелизм
Масштабирование достигается запуском нескольких процессов Uvicorn на разных портах 
Благодаря отсутствию состояния в памяти, запросы могут обрабатываться любым экземпляром

# Фактор 9: Утилизируемость
Приложение быстро запускается и корректно завершает работу 
Реализован эндпойнт /healthz для проверки жизнеспособности сервиса

# Фактор 10: Паритет окружений
Окружение разработки максимально приближено к продакшену ведь используется та же СУБД PostgreSQL, 
те же миграции Alembic и одинаковый механизм конфигурации через .env

# Фактор 11: Логи
Приложение выводит логи в стандартный поток вывода (stdout)
Не создаёт и не управляет лог-файлами
Логи могут быть перехвачены менеджером процессов или системой агрегации

# Фактор 12: Административные процессы
Задачи администрирования (миграции БД, заполнение тестовыми данными) выполняются 
как обычные процессы в том же окружении, используют тот же код и конфигурацию


# Дополнения из ревью

# Аутентификация
Реализована полностью:
- Регистрация и вход по email/паролю (POST /api/auth/register, /api/auth/login).
- Пароли хранятся только в виде хэша bcrypt; открытый пароль нигде не пишется.
- Авторизация через JWT (PyJWT, HS256), секрет и срок жизни токена — в .env.
- GET /api/auth/me возвращает текущего пользователя.
- Все CRUD-эндпойнты и агрегаты требуют валидный токен (заголовок
  Authorization: Bearer ...) и фильтруют данные по user_id текущего
  пользователя, обеспечивая изоляцию дневников.
- Фронтенд хранит токен в localStorage, автоматически проверяет его при
  загрузке страницы (/auth/me), обрабатывает 401 и предоставляет выход.

# Защита от XSS
Весь пользовательский ввод (названия продуктов, заметки, значения)
экранируется на фронтенде функцией escapeHtml() перед вставкой в DOM,
что исключает выполнение внедрённых скриптов.
