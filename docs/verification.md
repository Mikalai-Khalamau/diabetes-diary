# Верификация требований — Дневник диабетика

Документ сопутствует `docs/specification.md`. Цель — для каждого требования
задан способ проверки, непроверяемые формулировки переписаны, требования
сверены с работающим приложением и исходным кодом, расхождения зарегистрированы
в `ISSUES.md`.

## Методология сверки

Использованы три способа проверки (комбинируются по типу требования):

- **Инспекция кода** — чтение `backend/app/*` и `frontend/app.js` на предмет
  наличия заявленного поведения (guard-правила, валидация, экранирование,
  конфигурирование).
- **Ручная демонстрация / наблюдение в рантайме** — прогон приложения
  (UI + Swagger + логи контейнера) в ходе отладки: регистрация, вход,
  создание событий, лента/статистика, сидинг базового справочника.
- **Автоматические тесты (этап 2 задания)** — юнит/интеграционные/сценарные
  тесты pytest; на этапе 3 указан как способ проверки там, где эмпирический
  прогон ещё не выполнен, но поведение подтверждено инспекцией и расхождений
  не выявлено.

Условные обозначения результата сверки:
✅ — подтверждено (инспекция и/или рантайм); ◻ — подтверждается автотестами
этапа 2, инспекцией расхождений не выявлено; ⚠️ — выявлено расхождение или
ограничение (ссылка на дефект в `ISSUES.md`).

## Ревизия непроверяемых требований

Следующие формулировки из спецификации не допускали однозначного способа
проверки (субъективные критерии, утверждения о будущем без измеримого
инварианта). Они переписаны в проверяемую форму; исходный текст сохранён для
трассировки.

|---|---|---|---|---|

После ревизии все требования BR/UC/FR/NFR имеют хотя бы один формализуемый
способ проверки.

## Итог сверки

- По функциональным и бизнес-требованиям расхождений с работающим приложением
  и кодом не выявлено: поведение соответствует спецификации (часть подтверждена
  рантаймом и инспекцией, часть зарезервирована под автотесты этапа 2 без
  обнаруженных противоречий).
- По нефункциональным выявлены два ограничения объёма/реализации: отсутствие
  rate-limiting на аутентификации (NFR1 → ISSUE-6) и неподтверждённость
  временну́ю метрику производительности (NFR5 → ISSUE-5).
- Отдельный класс расхождений — несоответствие документации в репозитории
  (README, инструкция запуска, пример `.env`, связка `alembic`+`seed`)
  фактическому состоянию кода. Зафиксированы как ISSUE-1, ISSUE-2, ISSUE-3.
- Требование ТЗ о заглушках к внешним HTTP-сервисам признано неприменимым
  (исходящих интеграций нет) → ISSUE-4 (accepted N/A).

Все перечисленные расхождения и ограничения детализированы в `ISSUES.md`.
