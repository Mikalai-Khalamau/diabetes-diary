# План тестирования — Дневник диабетика

## 1. Цель тестирования
Целью тестирования является верификация соответствия веб-приложения «Дневник диабетика» заявленным бизнес, функциональным и нефункциональным требованиям (FR, NFR, UC) из спецификации, подтверждение корректности работы бизнес-логики бэкенда (FastAPI, SQLAlchemy), изоляции данных пользователей, механизмов безопасности (bcrypt, JWT), интерфейса и инфраструктурной составляющей (Docker, Minikube, VictoriaLogs).

---

## 2. Области, подвергаемые тестированию, и области вне тестирования

### 2.1. Подвергаемые тестированию области (In-Scope)
- **Модуль аутентификации и пользователей (FR1–FR6, UC1):** Регистрация, хэширование паролей (bcrypt), генерация/валидация JWT, защита эндпоинтов, изоляция данных (`user_id`).
- **Справочник продуктов (FR7–FR11, UC2):** Автоматическое создание базового набора при регистрации (>100 продуктов), CRUD-операции над продуктами, проверка уникальности имени, защита от удаления используемых в еде продуктов.
- **События глюкозы (FR12, UC3):** Ввод, валидация диапазона (0 < value ≤ 50), редактирование и удаление замеров сахара.
- **События инсулина (FR13, UC4):** Учёт инъекций (short/long), валидация типа и дозы (0 < dose ≤ 200).
- **Приёмы пищи и расчёт ХЕ (FR14–FR15, UC5):** Учёт еды, автоматический расчёт углеводов и хлебных единиц (ХЕ) по формуле, неизменяемость истории при правке справочника.
- **Лента событий и статистика (FR16–FR18, UC6):** Пагинация, лента за сегодня/вчера с учётом часового пояса, агрегированная статистика (среднее/мин/макс сахара, суммы инсулина и углеводов/ХЕ).
- **Системные эндпоинты и безопасность (FR19–FR20, NFR1–NFR6):** Проверка живости (`/healthz`), экранирование ввода на клиенте (защита от XSS), конфигурация через env, логирование в stdout, пуш в VictoriaLogs через Fluent Bit.

### 2.2. Области вне тестирования (Out-of-Scope)
- **NFR5 (Производительность / Нагрузочное тестирование):** Замер точного времени отклика под высокой нагрузкой (1000+ RPS) отнесён в отдельный backlog (см. `ISSUES.md`, ISSUE-5), так как в рамках текущей лабораторной работы упор сделан на функциональную и интеграционную верификацию.
- **Внешние исходящие HTTP-интеграции (ISSUE-4):** В приложении отсутствуют внешние API-вызовы наружу (интеграция идёт только с локальной СУБД PostgreSQL и логгированием), поэтому тесты внешних транспортных заглушек не требуются.
- **Rate-limiting на аутентификации (ISSUE-6):** Защита от брутфорса/DDoS на `/auth` не реализована в текущей учебной версии (зафиксировано в дефектах), функционал лимитирования не тестируется.

## 3. Тестовая стратегия

### 3.1. Уровни тестирования
1. **Модульное тестирование (Unit Testing):** Проверка отдельных функций и схем Pydantic, хэширования паролей, генерации/проверки JWT, валидации полей, формул расчёта ХЕ. Инструмент: `pytest` (файлы `tests/test_unit.py`).
2. **Интеграционное тестирование (Integration Testing):** Проверка взаимодействия эндпоинтов FastAPI с базой данных (PostgreSQL / TestClient) через SQLAlchemy сессии, проверка работы CRUD-слоя и изоляции `user_id`. Инструмент: `pytest` (`tests/test_integration.py`).
3. **Сценарное тестирование (Scenario / E2E Testing):** Проверка сквозных пользовательских сценариев (регистрация → авто-наполнение справочника → добавление продуктов, замера сахара, инсулина, приёма пищи → просмотр ленты и статистики). Инструмент: `pytest` (`tests/test_scenario.py`).
4. **Системное и UI-тестирование (System / Manual Testing):** Ручная проверка пользовательского интерфейса в браузере (включая Minikube/Docker развёртывание), проверка XSS-экранирования, наглядности статистики и навигации.
5. **Инфраструктурное тестирование / SRE:** Проверка работы liveness/readiness probes в Kubernetes, сбор логов через Fluent Bit и доставка в VictoriaLogs (проверка через VMUI).

### 3.2. Виды тестирования
- **Функциональное тестирование:** Проверка реализации всех FR и UC (позитивные и негативные сценарии).
- **Тестирование безопасности:** Проверка хэширования паролей, валидации JWT токенов, изоляции данных пользователей (предотвращение несанкционированного доступа к чужим записям).
- **Регрессионное тестирование:** Прогон автоматических тестов (`pytest`) при любых изменениях конфигурации или сборке образов.

## 4. Критерии тестирования

### 4.1. Критерии начала тестирования (Start Criteria)
- Репозиторий развёрнут, зависимости установлены (`pip install -r requirements.txt`).
- База данных доступна (PostgreSQL поднята через Docker Compose или протестирована через TestClient).
- Автоматические юнит- и интеграционные тесты успешно компилируются и готовы к запуску.

### 4.2. Критерии приостановки тестирования (Suspension Criteria)
- Критическая ошибка инфраструктуры (например, недоступность СУБД или падение FastAPI на старте из-за повреждённой конфигурации).
- Блокирующий дефект, препятствующий выполнению базового сценария регистрации/авторизации (нарушение FR1/FR3).

### 4.3. Критерии возобновления тестирования (Resumption Criteria)
- Инфраструктурная проблема устранена, соединение с БД восстановлено.
- Исправлен блокирующий дефект, пройден дымовой тест (smoke test) эндпоинта `/healthz` и авторизации.

### 4.4. Критерии приёмочные и завершения тестирования (Acceptance & Completion Criteria)
- **Покрытие тестами:** 100% функциональных требований с высоким приоритетом покрыты тест-кейсами.
- **Успешность прохождения:** 100% тест-кейсов с высоким приоритетом завершились со статусом `Passed`.
- **Дефекты:** Отсутствуют неисправленные дефекты с критическим (Critical) и высоким (High) приоритетом. Все выявленные средние/низкие дефекты задокументированы в `ISSUES.md`.

## 5. Метрики тестирования и формулы

Для оценки качества и полноты тестирования используются следующие метрики (согласно методическим указаниям, раздел 6.2):

1. **Процент успешного прохождения тест-кейсов (Test Pass Rate):**
   $$\text{Pass Rate} = \frac{\text{Number of Passed Test Cases}}{\text{Total Executed Test Cases}} \times 100\%$$
   *Целевое значение:* 100% для критических и высоких требований.

2. **Процент выполнения тест-кейсов (Test Execution Rate):**
   $$\text{Execution Rate} = \frac{\text{Number of Executed Test Cases}}{\text{Total Planned Test Cases}} \times 100\%$$
   *Целевое значение:* 100%.

3. **Покрытие требований тест-кейсами (Requirement Coverage):**
   $$\text{Req Coverage} = \frac{\text{Number of Requirements Covered by Test Cases}}{\text{Total Number of Defined Requirements}} \times 100\%$$
   *Целевое значение:* 100% для FR1–FR20.

4. **Процент устранения дефектов по важности (Defect Resolution Rate):**
   $$\text{Resolution Rate} = \frac{\text{Number of Fixed Defects}}{\text{Total Number of Reported Defects}} \times 100\%$$
   *Целевое значение:* 100% для Critical/High, приемлемо ≥ 80% с учётом принятых ограничений (`accepted` в `ISSUES.md`).
