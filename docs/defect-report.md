# Реестр дефектов и ошибок — Дневник диабетика

Ниже представлен отчёт о найденных дефектах и ограничениях, выявленных в ходе верификации и тестирования приложения (согласно реестру `ISSUES.md`).

---

## Дефект #1 (DEF-01 / ISSUE-2): Отставание миграций Alembic от актуальной схемы моделей
- **Краткое описание:** Миграции Alembic в репозитории не содержат таблицу `users` и колонку `user_id`, что может приводить к рассинхрону схемы БД при последовательном выполнении `alembic upgrade head` и сидинга.
- **Подробное описание:**
  - *Ожидаемое:* Миграции Alembic полностью отражают текущее состояние ORM-моделей (`models.py`), позволяя чисто развернуть схему через миграции.
  - *Фактическое:* Alembic-миграции отстают от моделей; комбинация `alembic upgrade head` с последующим `seed` (`create_all`) может вызвать рассинхрон колонок `user_id`.
  - *Ссылка на требование:* NFR3 (конфигурируемость и воспроизводимость развёртывания).
- **Шаги воспроизведения:**
  1. Выполнить `cd backend && alembic upgrade head`.
  2. Запустить скрипт сидинга `python -m scripts.seed`.
  3. Проверить структуру таблиц в PostgreSQL.
- **Воспроизводимость:** 100% на чистой базе при попытке использовать миграции.
- **Важность и срочность:** Важность — High, Срочность — Medium.
- **Симптом:** Ошибки отсутствия колонок `user_id` или таблиц при попытке мигрировать готовую базу данных.
- **Возможность обойти:** На текущем этапе схема инициализируется напрямую через `create_all` в скрипте сидинга / Docker Compose (без вызова `alembic upgrade head` на пустой базе).

## Дефект #2 (DEF-02 / ISSUE-6): Отсутствие rate-limiting на эндпоинтах аутентификации
- **Краткое описание:** Эндпоинты `/api/auth/register` и `/api/auth/login` не защищены от ограничения частоты запросов (rate-limiting).
- **Подробное описание:**
  - *Ожидаемое:* Эндпоинты аутентификации защищены от брутфорса и флуда (ограничение числа запросов в минуту с одного IP).
  - *Фактическое:* Повторные попытки `/login` или `/register` не блокируются системой.
  - *Ссылка на требование:* NFR1 (Безопасность).
- **Шаги воспроизведения:**
  1. Отправить серию из 100+ быстрых POST-запросов на `/api/auth/login` с неверными данными.
- **Воспроизводимость:** 100%.
- **Важность и срочность:** Важность — Medium, Срочность — Low.
- **Симптом:** Отсутствие блокировок при переборе паролей на уровне приложения.
- **Возможность обойти:** Для учебного однопользовательского дневника риск минимален; в продуктовой среде защита реализуется через middleware (`slowapi`) или на уровне reverse-proxy / Ingress (nginx / API Gateway).

## Дефект #3 (DEF-03 / ISSUE-3): Отсутствие обязательной переменной `SECRET_KEY` в исходном примере `.env.example`
- **Краткое описание:** Приложение падает с ошибкой валидации Pydantic при старте, если в окружении не задана переменная `SECRET_KEY`, при этом в оригинальном репозитории она отсутствовала в `.env.example`.
- **Подробное описание:**
  - *Ожидаемое:* Файл `.env.example` содержит все обязательные для старта параметры, включая `SECRET_KEY`.
  - *Фактическое:* Приложение выдавало `ValidationError` на импорте `config.py` при отсутствии `SECRET_KEY`.
  - *Ссылка на требование:* NFR3 (Конфигурируемость).
- **Шаги воспроизведения:**
  1. Удалить `SECRET_KEY` из окружения и запустить приложение `python run.py`.
- **Воспроизводимость:** 100%.
- **Важность и срочность:** Важность — High, Срочность — High.
- **Симптом:** Падение приложения при старте с ошибкой `ValidationError: Field required [type=missing, input_value={}, input_loc=('secret_key',)]`.
- **Возможность обойти:** Добавлена строка `SECRET_KEY` с дефолтным заглушечным значением в `.env.example` (устранено локально).
