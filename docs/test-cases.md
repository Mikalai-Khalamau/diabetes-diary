# Набор тест-кейсов — Дневник диабетика

Ниже представлен набор из 25+ детализированных тест-кейсов, покрывающих все функциональные требования приложения с высоким (High) и средним (Medium) приоритетом.

---

### TC-01: Успешная регистрация пользователя
- **ID:** TC-01
- **Приоритет:** High
- **Связанное требование:** FR1, UC1
- **Модуль/Подмодуль:** `auth` / Регистрация
- **Заглавие:** Успешная регистрация нового пользователя с валидными данными
- **Исходные данные:** База данных чиста или email `new_user@example.com` отсутствует в базе.
- **Шаги:**
  1. Выполнить `POST /api/auth/register` с телом `{"email": "new_user@example.com", "password": "SecurePassword123"}`.
- **Ожидаемый результат:** HTTP 201 Created (или 200 OK), пользователь успешно создан, в ответе отсутствуют данные пароля.

### TC-02: Регистрация с существующим email (конфликт)
- **ID:** TC-02
- **Приоритет:** High
- **Связанное требование:** FR1
- **Модуль/Подмодуль:** `auth` / Регистрация
- **Заглавие:** Ошибка 409 при попытке регистрации с уже занятым email
- **Исходные данные:** Пользователь с email `existing@example.com` уже зарегистрирован.
- **Шаги:**
  1. Выполнить `POST /api/auth/register` с телом `{"email": "existing@example.com", "password": "AnotherPassword123"}`.
- **Ожидаемый результат:** HTTP 409 Conflict, регистрация отклонена.

### TC-03: Валидация формата email при регистрации
- **ID:** TC-03

- **Связанное требование:** FR1
- **Модуль/Подмодуль:** `auth` / Регистрация
- **Заглавие:** Ошибка валидации при неверном формате email
- **Исходные данные:** API доступно.

- **Ожидаемый результат:** HTTP 422 Unprocessable Entity, Pydantic отвергает запрос из-за некорректного email.

### TC-04: Хэширование пароля в базе данных (bcrypt)
- **ID:** TC-04
- **Приоритет:** High
- **Связанное требование:** FR2, NFR1
- **Модуль/Подмодуль:** `auth` / Безопасность
- **Заглавие:** Проверка того, что пароль сохраняется в БД исключительно как bcrypt-хэш
- **Исходные данные:** Пользователь успешно зарегистрирован с паролем `Password123`.
- **Шаги:**
  1. Выполнить прямой запрос к таблице `users` в БД (или проверить через unit-тест `security.hash_password`).
- **Ожидаемый результат:** Колонка `password_hash` содержит строку, начинающуюся с `$2b$`, открытый текст `Password123` в базе отсутствует.

### TC-19: Автоматический расчёт углеводов и ХЕ при приёме пищи
- **ID:** TC-19
- **Приоритет:** High
- **Связанное требование:** FR14, UC5, UC5.1
- **Модуль/Подмодуль:** `meal-events` / Бизнес-логика
- **Заглавие:** Проверка авторасчёта `carbs_grams` и `bread_units` по справочнику и массе
- **Исходные данные:** Продукт «Овсянка» имеет 60г углеводов на 100г. Коэффициент ХЕ в конфиге = 12г.
- **Шаги:**
  1. Выполнить `POST /api/meal-events/` с телом `{"food_id": <id>, "grams": 150.0, "occurred_at": "..."}`.
- **Ожидаемый результат:** HTTP 200/201, `carbs_grams` рассчитывается как `150 * 60 / 100 = 90.0`, а `bread_units` как `90 / 12 = 7.5`.

- **Заглавие:** Убедиться, что правка углеводов в справочнике не пересчитывает прошлые приёмы пищи
- **Исходные данные:** Создан приём пищи с продуктом Х (углеводы 50г/100г). Зафиксировано `carbs_grams = 50`.
- **Шаги:**
  1. Изменить углеводы продукта Х в справочнике на 100г/100г (`PATCH /api/foods/{id}`).
  2. Запросить ранее созданный `MealEvent`.
- **Ожидаемый результат:** Значения `carbs_grams` и `bread_units` в историческом `MealEvent` остались прежними (50г / ХЕ), пересчёт не произошёл.
