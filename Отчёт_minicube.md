# Что было сделано

Наше приложение было запущено в локальном кластере minikube
Сначала был установлен и запущен minikube с Docker runtime
Затем через docker-env образ приложения был собран внутри докер-демона minikube
В папке k8s были подготовлены манифесты и применены командой kubectl apply -f k8s/
Кубер развернул базу данных, выполнил Job для заполнения базы и запустил приложение
Интерфейс через minikube service diabetes-app
Масштабирование приложения до нескольких реплик работает 

# Какие абстракции Kubernetes использованы для запуска

1. Pod - базовая единица запуска контейнеров
Внутри подов работали PostgreSQL, FastAPI и Job для заполнения базы
2. Deployment для долгоживущих сервисов: базы данных и приложения
Он описывает, сколько копий подов должно работать и какой образ использовать
3. ReplicaSet следит за тем, чтобы нужное количество подов оставалось запущенным
Он создавался автоматически через Deployment
4. Service использовался для стабильного сетевого доступа к подам 
Сервис diabetes-db давал приложению доступ к базе внутри кластера
Сервис diabetes-app давал доступ к веб-интерфейсу
5. ConfigMap для хранения конфигурации приложения 
Порт, часовой пояс, уровень логов, углеводы хлебных единиц
6. Secret хранит чувствительтные данные 
Пользователь и пароль Postgre, строка подключения к базе и секретный ключ для JWT
7. PersistentVolumeClaim - постоянное хранилище для Postgre
Благодаря этому данные базы не теряются после перезапуска пда
8. Job используется для разовой задачи
Заполняет базу данных и завершается
9. Labels и Selectors связывают сервисы и деплойменты с нужными подами
Поды приложения имели метку app=diabetes-app и сервис diabetes-app выбирал эти поды
10. Probes для проверки готовности
Приложение проверялось через эндпоинт /healthz, а база данных через pg_isready
11. Resources ограничивают CPU и память, чтобы приложение и база стабильно работали внутри миникуба

# Как сервисы приложения взаимодействуют между собой

Браузер обращается к приложению через minikube service diabetes-app
Этот запрос попадает на Service diabetes-app
Service выбирает один из подов Fast API приложения и направляет запрос в него

Приложение получает конфигурацию из ConfigMap и Secret
В Secret находится строка подключения DATABASE_URL, в которой хостом указано имя diabetes-db
Поэтому приложение обращается не к localhost, а к сервису базы данных внутри кластера

Service diabetes-db направляет запросы на под с Postgre 
Postgre хранит данные в PersistentVolumeClaim

Отдельно выполнился Job diabetes-seed
Он подключался к Postgre и выполнял скрипт scripts/seed
После этого в базе есть тестовый пользователь, справочник продуктов 

Масштабирование - kubectl scale deployment diabetes-app --replicas=3
После этого кубер создал три пода приложения, а Service diabetes-app начал распределять запросы между ними
Приложение не хранит сессию пользователя в памяти одного пода, а использует общую базу данных
