# ISSUES — реестр дефектов и расхождений

Формат записи: `ID | Тип | Приоритет | Связанное требование/раздел | Описание |
Шаги воспроизведения / источник | Ожидаемое | Фактическое | Статус`.

Статусы: `open` — не устранено; `fixed-local` — исправлено в рабочей копии,
требуется коммит/пуш в репозиторий; `accepted` — принято как обоснованное
ограничение объёма (N/A).

## ISSUE-1 — README в репозитории устарел и противоречит коду

- **Тип:** документация
- **Приоритет:** средний
- **Связано с:** раздел «Инструкция по сборке/запуску» README; NFR3; FR7, FR10, FR6
- **Описание:** опубликованный в репозитории `README.md` не отражает текущее
  состояние приложения и содержит противоречивые/устаревшие инструкции.
- **Источник / шаги:** сравнение `README.md` (remote) с `backend/app/*`,
  `frontend/*`, `.env.example`. Выявленные несоответствия:
  1. В разделе «Возможности» и стеке отсутствуют аутентификация (bcrypt/PyJWT),
     авто-наполнение базовым справочником (FR7), редактирование продуктов
     (FR10), изоляция данных по пользователю (FR6), зависимость `tzdata`.
  2. Шаг запуска даёт `uvicorn app.main:app --reload --host 0.0.0.0 --port 8000`,
     тогда как порт должен читаться из `.env` через `run.py` (NFR3, фактор 7);
     хардкод порта в команде противоречит конфигурируемости.
  3. Пример `docker run` использует плейсхолдеры `POSTGRES_USER=ПОЛЬЗОВАТЕЛЬ`,
     `POSTGRES_PASSWORD=ПАРОЛЬ` и порт `5433`, не согласованные со значениями
     `.env.example` (`app`/`app`) и с внутренним портом compose (`db:5432`);
     не указано явное создание БД `diary`.
- **Ожидаемое:** README описывает фактический API/поведение и актуальные команды
  запуска (run.py / docker compose, порт и SECRET_KEY из `.env`).
- **Фактическое:** README описывает состояние до добавления auth/справочника и
  предлагает запуск с хардкод-портом.
- **Статус:** `fixed-local` — локальный `README.md` обновлён (добавлены целевые
  пользователи, архитектура, модули, точки интеграции, auth/справочник в
  возможностях и стеке, запуск через `run.py`/compose, `SECRET_KEY` в примере
  `.env`); требуется закоммитить и запушить в репозиторий.

## ISSUE-2 — связка `alembic upgrade head` + `seed` ненадёжна (миграции не отражают схему)

- **Тип:** документация / миграции
- **Приоритет:** высокий
- **Связано с:** раздел запуска README (шаг «Применить миграции»); NFR3
- **Описание:** инструкция репозитория предписывает `cd backend && alembic
  upgrade head` перед `python -m scripts.seed`. Однако alembic-миграции в
  репозитории не содержат таблицу `users` и колонку `user_id` (они появились в
  моделях позже генерации миграций). `Base.metadata.create_all` в `seed`
  создаёт отсутствующие таблицы, но **не добавляет колонки** в уже
  существующие: если `alembic upgrade head` сначала создал `foods`/события по
  старой схеме (без `user_id`), последующий `seed` не补齐 эти колонки, и
  ORM-модели разойдутся со схемой БД (ошибки при запросах с фильтром по
  `user_id`, нарушение FK/unique).
- **Источник / шаги:** чтение `backend/alembic/versions/*` (нет миграций на
  `users`/`user_id`) + поведение `create_all` (only-missing-tables).
- **Ожидаемое:** либо миграции покрывают текущую схему (тогда `upgrade head`
  + `seed` безопасны), либо инструкция не смешивает alembic и create_all.
- **Фактическое:** миграции отстают от моделей; комбинация `upgrade head`→`seed`
  может дать рассинхрон схемы. Рабочий путь на текущем этапе — `seed` с
  `create_all` на чистой БД (`docker compose down -v` + `up --build`), без
  предварительного `alembic upgrade head`.
- **Статус:** `open` — требуется либо сгенерировать автогенерацией миграцию на
  `users` + `user_id` (+ unique-констрейнт `(user_id,name)`), либо убрать
  `alembic upgrade head` из инструкции запуска и явно указать, что на данном
  этапе схема создаётся `seed`/`create_all`, а alembic подключается при
  появлении последующих изменений схемы.

## ISSUE-3 — в примере конфигурации отсутствует обязательный `SECRET_KEY`

- **Тип:** документация / конфигурация
- **Приоритет:** высокий
- **Связано с:** NFR3 (конфигурируемость), FR4 (авторизация по JWT)
- **Описание:** `backend/app/config.py` объявляет `secret_key: str` без значения
  по умолчанию, поэтому приложение **не стартует** при отсутствии переменной
  `SECRET_KEY` (валидация pydantic-settings падает на импорте `settings`).
  Опубликованный README/`.env`-инструкции репозитория не показывают это поле и
  не объясняют его обязательность, что приводит к сбою запуска у проверяющего.
- **Источник / шаги:** `python run.py` без `SECRET_KEY` в окружении →
  `ValidationError` на старте; сравнение с `.env.example` (в рабочей копии поле
  присутствует со значением-заглушкой `CHANGE_ME_...`).
- **Ожидаемое:** `.env.example` и README содержат `SECRET_KEY` с пометкой об
  обязательности и указанием сгенерировать собственный ключ для прода.
- **Фактическое:** в remote-документации поле не упомянуто.
- **Статус:** `fixed-local` — `.env.example` и локальный README дополнены
  `SECRET_KEY`/`ALGORITHM`/`ACCESS_TOKEN_EXPIRE_MINUTES` с комментарием об
  обязательности; требуется пуш.

## ISSUE-4 — исходящие внешние HTTP-интеграции отсутствуют (требование о заглушках неприменимо)

- **Тип:** ограничение объёма (N/A)
- **Приоритет:** низкий
- **Связано с:** задание 2.1 («заглушки на уровне HTTP-запросов для внешних
  сервисов»); раздел README «Точки интеграции»
- **Описание:** в текущей версии приложения нет вызовов внешних HTTP/REST-
  сервисов (все интеграции — входящий API, БД, файловая система). Поэтому
  подпункт ТЗ о стабах исходяших HTTP-запросов не имеет объекта применения.
- **Источник / шаги:** инспекция `backend/app/*` — отсутствие httpx/requests/
  urllib-вызовов наружу; README «Точки интеграции» явно фиксирует «исходящие
  внешние сервисы отсутствуют».
- **Ожидаемое (по ТЗ):** демонстрация заглушки внешнего HTTP-сервиса.
- **Фактическое:** внешних сервисов нет; техника подмены зависимостей
  демонстрируется на внутренних границах (`dependency_overrides` для
  `get_db`/`get_current_user` в этапе 2), HTTP-поведение приложения проверяется
  через `TestClient`.
- **Статус:** `accepted` — обоснованное N/A; при появлении outbound-интеграции
  (например, сервис уведомлений) требование закрывается стабом на уровне
  транспортного клиента.

## ISSUE-5 — временну́я метрика производительности не подтверждена эмпирически

- **Тип:** ограничение верификации
- **Приоритет:** низкий
- **Связано с:** NFR5 (переписанная формулировка)
- **Описание:** после ревизии NFR5 разбит на проверяемые структурные
  инварианты (пул `pool_pre_ping`, пагинация `limit`, индексы) — они
  подтверждены инспекцией. Пороговая временну́я метрика (время отклика) не
  может быть верифицирована без нагрузочного тестирования, которое выходит за
  объём данного задания.
- **Источник / шаги:** инспекция `database.py`/`models.py`/`crud.py` (инварианты
  ✅); отсутствие нагрузочного стенда/скрипта (метрика ◻/⚠️).
- **Ожидаемое:** либо измеренная метрика, либо явная фиксация, что метрика —
  цель отдельного нагрузочного теста.
- **Фактическое:** инварианты подтверждены, метрика не измерена.
- **Статус:** `accepted` — инварианты NFR5 верифицированы; временну́я метрика
  перенесена в backlog нагрузочного тестирования (вне объёма ДЗ).

## ISSUE-6 — отсутствует rate-limiting на эндпоинтах аутентификации

- **Тип:** дефект безопасности (известное ограничение)
- **Приоритет:** средний
- **Связано с:** NFR1 (безопасность), FR1/FR3
- **Описание:** `/api/auth/register` и `/api/auth/login` не защищены от
  перебора/флуда (нет ограничения частоты запросов, нет блокировки после
  неудачных попыток). Для учебного single-user-дневника риск приемлем, но это
  незакрытая часть NFR1.
- **Источник / шаги:** инспекция `api/auth.py` и `main.py` — отсутствие
  middleware лимитирования; попытка повторных `/login` с неверным паролем не
  блокируется.
- **Ожидаемое (полная форма NFR1):** ограничение частоты на auth-эндпоинтах.
- **Фактическое:** защита не реализована.
- **Статус:** `open` — зафиксировано как известное ограничение; при
  доработке добавляется rate-limit middleware (например, slowapi) либо выносится
  на уровень reverse-proxy/балансировщика (перекликается с будущими ДЗ по
  балансировке трафика).
